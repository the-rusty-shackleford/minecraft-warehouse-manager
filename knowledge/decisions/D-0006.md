# D-0006 — A warehouse has an owner, and its conveniences and containers are bound to who the owner trusts

Proposed 2026-09-24 from Rusty's request that evening; accepted the same day on Rusty's "build
D-0006" and built as 0.3.0. Rusty settled each part in turn (below); the three open points at
the end were called during the build as recorded there, and stay Rusty's to overturn.

Rusty: "Several actions should be identity bound so that someone can't just walk up to your
crafting station and start crafting using all your stuff, whether maliciously or accidentally."
Then: trust is managed from the manager's own UI by clicking players; a stranger must not get
around it "by just placing their own manager block next to mine"; and "I want the chests
refusing non-trusted players too."

## Identity

The manager block is owned by whoever placed it; the block entity persists the owner's UUID and
last-known name (names change). One owner per manager, any number of managers per player.
Transfer is by replacement. A manager placed before this version has no owner and stays open to
everyone until its first sneak-right-click claims it (first claimant wins, logged).

Three tiers: owner, trusted, everyone else. No bypass for operators or creative by default; a
config flag `operators_bypass` (off) exists for administration by hand.

## Trust from the manager's UI

Right-clicking the manager still opens its six-row drop-in inventory; the screen gains a panel
beside it headed with the owner's name, listing every player this world has ever seen (the
player-data directory, names through the server's profile cache; confirm the cache exposes what
is needed), online first and marked, each row a toggle. Only the owner's client gets a live
panel; everyone else sees it greyed under "Owned by <name>", which also explains why nothing
pulls for them. A toggle is a packet the server applies only from the owner. The roster lives on
the block entity with the owner.

Rejected: an invite handshake on the block and a `/warehouse trust` command (Rusty prefers the
list); a roster on a sign (anyone can rewrite a sign); scoreboard teams (op-managed, shared
with every mod that reads them).

## Which actions are bound

| Action | Owner / trusted | Everyone else |
|---|---|---|
| Recipe book sees the building's stock (D-0004 tally) | yes | no: vanilla, own inventory only |
| Crafting grid draws from the chests (D-0004 pull) | yes | no: vanilla fill |
| Opening the manager's drop-in inventory | yes | refused, action bar "<owner>'s warehouse" |
| Dropping chest items to furnish (D-0003) | yes | refused, same message |
| Right-click status report | yes | owner's name only |
| Opening a claimed container | yes | refused, same message |
| Breaking a claimed container or the manager | yes | refused |
| Explosions | claimed containers and the manager are removed from the explosion's block list |

Seeing is bound because the tally is exactly what the owner has. Breaking is bound because
refusing the open is pointless otherwise, and breaking the manager would release every claim.
Explosions are covered because they are the third way in. Revoking trust closes any of the
owner's containers that player has open. The manager keeps sorting, routing and furnishing: it
acts as a block entity, not a player.

Accidental drain by the owner: the pooled draw covers only what the grid will craft on this
click (one craft on a plain click, a stack's worth on shift-click), never the whole warehouse
count; the book still shows the true craftable count. D-0004's "ingredients drawn but not
crafted stay with the player" stands, but there are far fewer of them.

## No second manager in the building

1. **One building, one manager, the older one wins.** A walk that touches another manager's
   block is the same building. Placing a manager into a building that already has one is
   refused: the walk runs once at placement (milliseconds at the 20,000-cell cap), the item
   pops back, the action bar names whose manager is there and where. A manager in the shed
   next door is a different building, as the walk stops at solid blocks. A stranger who knocks
   a hole through the shared wall has put their manager in yours: it yields, and the older
   manager then claims the chests on their side. Accepted and documented rather than special-
   cased. Rejected: placing the second manager inert, which invites confusion.
2. **Claims persist** in saved level data instead of memory, so a container stays its
   manager's while unloaded and while the owner is offline. A claim is released only when the
   claimant block is broken or the container is gone; the manager re-checks its claims on load.
   Today (`Managers.claim`) an unloaded manager's claims fall to any loaded one, which is the
   hole rule 2 closes.
3. Pooled crafting is bound to the building's manager: with rules 1 and 2 there is no second
   manager to be near, so a stranger's own roster grants nothing here.

## The limit that remains

Hoppers. Anyone can place blocks inside the building, and a hopper under a claimed chest
drains it with no player interaction to refuse. Closing that means refusing block placement
by non-trusted players inside an owned building, which is a land-claim feature and a separate
decision. The README says so plainly.

## Verification

A JDK-only `Access` policy in `src/domain` with JUnit over the tiers and every bound action; a
GameTest with two mock players where the owner crafts from the chests and the stranger gets
vanilla behaviour, the refused open and the refused break; a GameTest that refuses the second
manager through a hole in the wall and lets the older one claim across it; a GameTest that an
explosion beside a claimed chest leaves it standing; a booth photo of the panel and of the
refusal on the action bar. The booth runs with EMI (D-0005).

## The open points, as called in the build

- **Explosion protection ships as written**, for every manager and every claimed container,
  owned or not: it is a property of the warehouse, not of a player, and a legacy manager's
  chests are no less worth keeping. One line in `Guard.detonate` would restrict it to owned
  managers if Rusty prefers.
- **The hopper gap stays documented** (README, "The limit that remains"). Refusing block
  placement inside an owned building is land claiming, a decision of its own.
- **Wording.** Open: "<owner>'s warehouse. You're not on the trusted list." Break: "<owner>'s
  warehouse. Only trusted players can break that." Placement: "<owner>'s manager already runs
  this building (at x, y, z)." or, unowned, "A manager already runs this building (at x, y,
  z)." Claiming: "This warehouse is now yours. Open it to choose who else may use it." The
  panel: "Your warehouse" / "<owner>'s warehouse" / "Unclaimed warehouse", with a one-line
  hint under each. All in `en_us.json`.
